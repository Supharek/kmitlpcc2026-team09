"เราออกแบบหน้าแรกให้สื่อสารธุรกิจและสร้างความน่าเชื่อถือทันที (G1, G3) เพื่อดึงความสนใจ จากนั้นจึงแยกหน้าบริการและเกี่ยวกับเราเพื่อลงรายละเอียดเชิงลึก (G2, G3) โดยไม่ทำให้หน้าแรกยาวเกินไป ส่วนหน้าติดต่อถูกแยกออกมาเพื่อให้ลูกค้าโฟกัสกับการส่งข้อมูล (G4) ได้ง่ายที่สุด พร้อมกับสร้างหน้า /admin แยกไว้หลังบ้านเพื่อความปลอดภัยในการทำงานของทีม (G6, G7)"

### 2.4 ทางเลือกที่พิจารณาแล้วไม่เอา
1. Landing Page แบบหน้าเดียวยาว

ทีมเคยพิจารณาการรวมเนื้อหาทั้งหมดไว้ในหน้า Home หน้าเดียว แต่ไม่เลือกใช้ เนื่องจากข้อมูลเกี่ยวกับบริษัท บริการ และช่องทางการติดต่อมีรายละเอียดค่อนข้างมาก การรวมทุกส่วนไว้ในหน้าเดียวอาจทำให้ผู้เข้าชมค้นหาข้อมูลได้ยากและหน้าเว็บมีความยาวมากเกินไป จึงเลือกแยกเป็นหน้า Home, About, Service และ Contact เพื่อให้แต่ละหน้ามีเป้าหมายที่ชัดเจน

2. ระบบสมาชิกสำหรับผู้เข้าชม

ทีมพิจารณาการสร้างระบบสมัครสมาชิกและ Login สำหรับลูกค้า แต่ไม่เลือกใช้ เนื่องจากไม่จำเป็นต่อเป้าหมายหลักของเว็บไซต์ ซึ่งเน้นการให้ข้อมูลบริการและรับข้อมูลติดต่อจากผู้สนใจ การเพิ่มระบบสมาชิกจะเพิ่มความซับซ้อนโดยไม่จำเป็นต่อขอบเขตของโครงงานในรอบนี้

3. ระบบข่าว/บทความแบบเต็มรูปแบบ

ทีมพิจารณาการสร้างระบบจัดการข่าวและบทความ แต่ยังไม่เลือกทำในรอบนี้ เนื่องจาก G5 เป็นระดับ Should และทีมต้องให้ความสำคัญกับ Requirement ระดับ Must ได้แก่ G1–G4 และ G7 ก่อน

### 3.4.1 หน้าที่มีฟอร์ม (T2) — ต้องระบุให้ครบทุกข้อ

- **ฟอร์มนี้อยู่ที่หน้าไหน:** `/contact`

- **ฟิลด์ทั้งหมด:**

| ฟิลด์ | ชนิด | บังคับ | กฎ validate | ข้อความ error ภาษาไทย |
|---|---|---|---|---|
| ชื่อ-นามสกุล | text | ใช่ | ความยาว 2–100 ตัวอักษร | `กรุณากรอกชื่อ-นามสกุล` |
| บริษัท / องค์กร | text | ไม่ | ไม่เกิน 150 ตัวอักษร | `ชื่อบริษัทต้องมีความยาวไม่เกิน 150 ตัวอักษร` |
| อีเมล | email | ใช่ | ต้องเป็นรูปแบบอีเมลที่ถูกต้อง และไม่เกิน 255 ตัวอักษร | `กรุณากรอกอีเมลให้ถูกต้อง` |
| เบอร์โทรศัพท์ | tel | ใช่ | ต้องเป็นหมายเลขโทรศัพท์ที่ถูกต้อง 9–10 หลัก | `กรุณากรอกเบอร์โทรศัพท์ให้ถูกต้อง` |
| บริการที่สนใจ | select | ใช่ | ต้องเลือกจากรายการบริการที่ระบบกำหนด | `กรุณาเลือกบริการที่สนใจ` |
| รายละเอียดโปรเจกต์ | textarea | ใช่ | ความยาว 10–2000 ตัวอักษร | `กรุณากรอกรายละเอียดโปรเจกต์อย่างน้อย 10 ตัวอักษร` |
| งบประมาณโดยประมาณ | select | ไม่ | ต้องเลือกจากตัวเลือกที่ระบบกำหนด | `กรุณาเลือกช่วงงบประมาณที่ถูกต้อง` |
| ยินยอมตาม PDPA | checkbox | ใช่ | ต้องมีค่าเป็น true | `กรุณายอมรับเงื่อนไขการใช้ข้อมูลก่อนส่งแบบฟอร์ม` |

**ตัวเลือกบริการที่สนใจ:**

- `Website Development`
- `Web Application`
- `Mobile Application`
- `UX/UI Design`
- `Custom Software`

- **ส่งสำเร็จแสดงอะไร:** `ส่งข้อมูลเรียบร้อยแล้ว เราจะนำรายละเอียดของคุณไปศึกษาและติดต่อกลับโดยเร็วที่สุด`

- **ส่งไม่สำเร็จแสดงอะไร:** `ไม่สามารถส่งข้อมูลได้ กรุณาตรวจสอบข้อมูลและลองใหม่อีกครั้ง`

- **ระหว่างกำลังส่งแสดงอะไร:** `กำลังส่งข้อมูล...`

**สถานะของฟอร์ม:**

| สถานะ | ผู้ใช้เห็นอะไร | ข้อความจริง |
|---|---|---|
| ปกติ | ฟอร์มพร้อมกรอกข้อมูล | `ส่งรายละเอียดโปรเจกต์` |
| กำลังส่ง | ปุ่มถูก disable และแสดง loading | `กำลังส่งข้อมูล...` |
| สำเร็จ | กล่องข้อความยืนยันการส่งข้อมูล | `ส่งข้อมูลเรียบร้อยแล้ว เราจะนำรายละเอียดของคุณไปศึกษาและติดต่อกลับโดยเร็วที่สุด` |
| ผิดพลาด | กล่องข้อความแจ้งเตือน | `ไม่สามารถส่งข้อมูลได้ กรุณาตรวจสอบข้อมูลและลองใหม่อีกครั้ง` |

**Data Flow ของฟอร์ม:**

`Contact Form → POST /api/leads → Zod Server Validation → Supabase PostgreSQL → บันทึก Lead → Response สำเร็จ`

### 4.4 การอ่านข้อมูลกลับจาก Database

Admin Dashboard ต้องอ่านข้อมูลจาก Supabase PostgreSQL เพื่อแสดง:

1. จำนวน Leads ทั้งหมด
2. จำนวน Leads ใหม่
3. จำนวน Leads ที่กำลังดำเนินการ
4. จำนวนการเข้าใช้งานเว็บไซต์ทั้งหมด
5. รายการ Leads ล่าสุด
6. รายละเอียดของ Lead ที่เลือก

ดังนั้นระบบจะแสดงข้อมูลจริงจาก Database ไม่ใช่ข้อมูลตัวอย่างที่เขียนตายตัวในหน้าเว็บ เพื่อให้ผ่าน T3

### 4.5 API ที่ต้องมี

| Method | Endpoint | หน้าที่ |
|---|---|---|
| GET | `/api/health` | ตรวจสอบว่า API และระบบสามารถทำงานได้ |
| POST | `/api/leads` | รับข้อมูลจาก Contact Form และบันทึกลง `leads` |
| POST | `/api/visits` | บันทึกการเข้าใช้งานเว็บไซต์ |
| GET | `/api/admin/leads` | อ่านข้อมูล Leads สำหรับ Admin |
| PATCH | `/api/admin/leads/:id` | เปลี่ยนสถานะ Lead |

ข้อมูลจากทุก input ที่ส่งเข้า Server ต้องผ่าน Zod validation ก่อนบันทึกลง Database

## 5. กฎทางธุรกิจ

- BR1: ผู้ใช้ต้องยอมรับ PDPA ก่อนจึงสามารถส่งข้อมูลติดต่อได้
- BR2: Lead ใหม่ทุกครั้งจะถูกสร้างด้วยสถานะ `NEW`
- BR3: ผู้ใช้สามารถส่งแบบฟอร์มซ้ำได้ หากต้องการติดต่อเกี่ยวกับโปรเจกต์อื่น โดยระบบไม่บังคับให้อีเมลไม่ซ้ำ
- BR4: ฟิลด์ที่กำหนดเป็น Required ต้องผ่านการตรวจสอบทั้งฝั่ง Client และ Server
- BR5: Server ต้องใช้ Zod ตรวจสอบข้อมูลทุก field ก่อนบันทึกลง Database
- BR6: ข้อมูล Lead สามารถอ่านและแก้ไขสถานะได้เฉพาะผู้ดูแลระบบที่ผ่านการยืนยันตัวตนแล้ว
- BR7: สถานะ Lead สามารถเปลี่ยนได้เฉพาะค่าที่ระบบกำหนด ได้แก่ `NEW`, `CONTACTED`, `DISCUSSING`, `QUOTATION`, `CLOSED`
- BR8: เมื่อส่งแบบฟอร์มสำเร็จ ระบบต้องบันทึกวันและเวลาที่สร้าง Lead โดยอัตโนมัติ
- BR9: การนับจำนวนการเข้าใช้งานเว็บไซต์เป็นจำนวนการเข้าชมรวม ไม่ใช่การระบุตัวตนผู้ใช้งานแต่ละบุคคล
- BR10: การเก็บข้อมูลการเข้าใช้งานเว็บไซต์จะไม่เก็บข้อมูลส่วนตัวที่ไม่จำเป็นต่อการนับจำนวนการเข้าชม
- BR11: หากข้อมูลไม่ผ่านการตรวจสอบ Server ต้องไม่บันทึกข้อมูลลง Database และต้องส่งข้อความ error ภาษาไทยกลับไป
- BR12: หากเกิดข้อผิดพลาดระหว่างการบันทึกข้อมูล ระบบต้องแจ้งผู้ใช้ว่าไม่สามารถส่งข้อมูลได้และไม่แสดงข้อมูลภายในของ Server
- BR13: ผู้ดูแลระบบต้องเข้าสู่ระบบก่อนดูข้อมูล Lead และสถิติการใช้งานเว็บไซต์
- BR14: เมื่อผู้ใช้ส่งแบบฟอร์มสำเร็จ ระบบต้องแสดงข้อความยืนยันให้ผู้ใช้ทราบทันที
- BR15: หากผู้ใช้เข้าหน้า `/contact?service=...` ระบบสามารถเลือกบริการในฟอร์มให้ตรงกับบริการที่ผู้ใช้เลือกมาจากหน้า Services
