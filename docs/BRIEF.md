# ส่วนที่ 1 · โจทย์

สร้าง **เว็บไซต์บริษัท** สำหรับบริษัทสมมติที่ทีมกำหนดเอง

> ⚠️ **โจทย์นี้ไม่ได้บอกว่าเว็บต้องมีหน้าอะไรบ้าง — นั่นคืองานของทีม**
> สิ่งที่กำหนดให้คือ *ผลลัพธ์ที่ต้องเกิดกับผู้เข้าชม* (G) และ *เกณฑ์ที่ทุกทีมต้องมีเหมือนกัน* (T)
> ทีมเป็นผู้ตัดสินใจเองว่าจะแปลงเป็นกี่หน้า หน้าอะไร ชื่อ URL อะไร จัดข้อมูลยังไง
> **แต่ละทีมจะได้ sitemap ไม่เหมือนกัน — และนั่นถูกต้องแล้ว**

## เป้าหมายที่เว็บต้องทำให้ได้ (G)

เขียนในรูป "ผู้เข้าชมต้องทำอะไรได้" ไม่ใช่ "ต้องมีหน้าอะไร"

| # | ผู้เข้าชมต้องทำสิ่งนี้ได้ | ระดับ |
|---|---|---|
| G1 | เข้าใจภายใน 10 วินาทีแรกว่าบริษัททำอะไร ให้ใคร | Must |
| G2 | หาข้อมูลสินค้า/บริการได้ละเอียดพอที่จะตัดสินใจว่าตรงกับความต้องการไหม | Must |
| G3 | ประเมินความน่าเชื่อถือของบริษัทได้ (เราคือใคร ผลงาน ประสบการณ์ ทีม) | Must |
| G4 | **ส่งข้อมูลติดต่อกลับมาได้ และข้อมูลนั้นถูกบันทึกไว้ให้ฝ่ายขายตามงานต่อ** | Must |
| G5 | ติดตามความเคลื่อนไหวของบริษัทได้ (ข่าว/บทความ/ผลงานใหม่) | Should |
| G6 | ทีมงานบริษัทเข้ามาดูข้อมูลที่ผู้เข้าชมส่งเข้ามาได้ | Could |

**ตัวอย่างการแปลงเป็นหน้า** — นี่เป็นแค่ *ตัวอย่างหนึ่ง* ห้าม copy ทั้งดุ้น
> ทีม A แปลง G1–G4 เป็น 4 หน้า: `/` `/about` `/services` `/contact`
> ทีม B แปลงเป็น 3 หน้า: `/` (รวม G1+G3), `/solutions/[slug]` (G2), `/quote` (G4)
> ทีม C ทำ landing page เดียวยาว ๆ (G1–G3) แล้วแยกแค่ `/contact`
>
> **ทั้งสามแบบผ่านเกณฑ์หมด** ถ้าอธิบายใน `SPEC.md` ได้ว่าทำไมถึงเลือกแบบนั้น

## สิ่งที่ทุกทีมต้องมีเหมือนกัน (T)

มีไว้เพื่อให้ครอบคลุมเนื้อหาที่วิชานี้ต้องสอน ไม่ใช่ข้อจำกัดด้านดีไซน์

| # | เกณฑ์ |

| T3 | มีอย่างน้อย **1 จุดที่แสดงข้อมูลซึ่งอ่านมาจากฐานข้อมูล** |

## คุณภาพที่ต้องผ่าน (N)

| # | หัวข้อ | เกณฑ์ |
|---|---|---|
| N1 | SEO | ทุกหน้ามี `<title>` และ meta description ไม่ซ้ำกัน |

## ไม่ต้องทำ

## เกณฑ์ส่งงาน
1. Deploy ขึ้น production URL สำเร็จ (Instructor เป็นคน merge `dev` → `main`)
2. `npm run verify` ผ่านทั้งหมด
3. `docs/` ครบและตรงกับโค้ดจริง
4. Commit history เห็นการทำงานของทุกบทบาท
5. **`SPEC.md` §2 อธิบายได้ว่าแต่ละหน้าที่ทีมออกแบบ ตอบเป้าหมาย G ข้อไหน**
   ถ้ามีหน้าที่ไม่ตอบ G ข้อไหนเลย ต้องอธิบายว่าทำไมยังต้องมี

# ส่วนที่ 3 · Vercel กับ Supabase ทำงานยังไง

## Vercel ไม่ใช่เครื่องเซิร์ฟเวอร์

Vercel = **CDN + ฟังก์ชันที่เกิดตอนมี request แล้วตายไป** (serverless)

| ทำได้ | ทำไม่ได้ |
|---|---|
| เสิร์ฟหน้าเว็บ static / SSR | รัน process ค้างไว้ (daemon, worker) |
| REST API แบบ request → response | เปิด WebSocket server เอง |
| อ่าน/เขียน DB ที่อยู่ข้างนอก | **โฮสต์ MySQL/Postgres บน Vercel** |
| อ่านไฟล์ที่ deploy ไปด้วย | เขียนไฟล์ถาวรลงดิสก์ (หายทุก request) |

> **จำประโยคนี้:** อะไรที่ต้อง "จำข้ามคำขอ" ต้องเก็บใน **ฐานข้อมูล** เท่านั้น

## ฐานข้อมูลมาจากไหน

Instructor สร้าง Supabase ให้แล้วผ่าน Vercel → Storage → *Connect to Project*
Vercel จึง **ใส่ environment variable ให้อัตโนมัติ**:

```
NEXT_PUBLIC_SUPABASE_URL        NEXT_PUBLIC_SUPABASE_ANON_KEY
SUPABASE_SERVICE_ROLE_KEY       POSTGRES_URL
```

**ตอนรันในเครื่อง ให้สร้าง `.env.local` เอง** จากค่าที่ Instructor ส่งให้
วิธีทำอยู่ใน `README.md` หัวข้อ *Environment variables*

## เรื่องที่พังบ่อยที่สุด — วิธีต่อฐานข้อมูล

| วิธี | พอร์ต | ใช้ตอนไหน |
|---|---|---|
| ✅ `@supabase/supabase-js` | 443 HTTPS | **โค้ดในแอป** — ไม่มี connection ค้าง ปลอดภัย |
| ⚠️ Transaction pooler | 6543 | ถ้าจำเป็นต้องเขียน SQL ตรงจากแอป |
| ❌ Direct connection | 5432 | **DBeaver / รัน migration เท่านั้น — ห้ามใช้ในโค้ดที่ deploy** |

เพราะทุก request อาจเกิด function instance ใหม่ ถ้าแต่ละตัวเปิด TCP ไป 5432
Postgres จะเต็มโควตาแล้วขึ้น `too many connections` — **เว็บล่มทั้งเว็บพร้อมกัน**

## เส้นทางข้อมูล (ห้ามลัด)

```
Browser  ──HTTPS──▶  Route Handler (app/api/**)  ──HTTPS──▶  Supabase
                     ▲ ใช้ SUPABASE_SERVICE_ROLE_KEY ที่นี่ที่เดียว
```

- ❌ ห้ามเรียก Supabase จาก Client Component ด้วย `service_role` key
- ❌ ห้ามตั้งชื่อ env ที่เป็นความลับขึ้นต้นด้วย `NEXT_PUBLIC_` (Next.js จะฝังลงหน้าเว็บให้ทุกคนเห็น)
- ✅ เปิด RLS ทุกตาราง — ถือว่า `anon` key เป็นของสาธารณะ เพราะมันอยู่ในหน้าเว็บจริง ๆ

## ข้อจำกัดที่กระทบเรา

| เรื่อง | ค่า | ผล |
|---|---|---|
| Build พร้อมกัน | **1 งานต่อ account** | 10 ทีม merge พร้อมกัน → ต่อคิว |
| Deploy ต่อวัน | 100 ทั้ง account | จึง build เฉพาะ `main` |
| Request/Response body | 4.5 MB | ไฟล์ใหญ่ต้องยิงตรงเข้า Supabase Storage |
| Runtime logs | เก็บ **1 ชั่วโมง** | พังแล้วต้องรีบดู |
| Supabase Free | ไม่ใช้ 7 วันจะ pause | ก่อนนำเสนอให้เข้าไปปลุกก่อน |
| Hobby plan | **ห้ามใช้เชิงพาณิชย์** | ใช้เพื่อการเรียนเท่านั้น |

## deploy พังให้ไล่ตามนี้

1. **Environment Variables ใน Vercel ไม่ครบ** ← เจอบ่อยที่สุด
2. **ตัวพิมพ์ใหญ่-เล็กของชื่อไฟล์ไม่ตรงกับ import** — Windows ไม่สนใจ แต่ Linux บน Vercel สนใจ
3. รัน `npm run verify` ในเครื่อง — ส่วนใหญ่พังตั้งแต่ตรงนี้
4. เปิด Vercel → Deployments → อ่าน build log จริง อย่าเดา
