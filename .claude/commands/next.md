## ขั้นที่ 1 — เลือกงาน

1. อ่าน `docs/TASKS.md` หา task แรกที่ยังไม่ติ๊ก และเป็นของบทบาท **$ARGUMENTS**
2. เช็ค dependency — ถ้ายังไม่เสร็จ ให้บอกว่าติดอะไรแล้วหยุด
3. อ่าน `docs/SPEC.md` และ `docs/DESIGN.md` เฉพาะส่วนที่เกี่ยวกับ task นี้
   **ถ้า task นี้แตะหน้าเว็บ — ต้องเปิดดูรูปใน `docs/wireframes/` ของหน้านั้นด้วย**
   (ชื่อไฟล์อยู่ในตารางของหน้านั้น) แล้วเอา *ข้อความ* จากตาราง เอา *layout* จากรูป
4. สรุปแผนว่าจะแก้ไฟล์ไหนบ้าง **รอผู้ใช้ยืนยันก่อนลงมือ**

## ขั้นที่ 2 — ทำ

- แก้เฉพาะไฟล์ในขอบเขตบทบาท (ตาราง §4 ใน `AGENTS.md`)
- ไม่เกิน 3–5 ไฟล์ต่อรอบ
- เจอสเปกกำกวม → จดลง `docs/NOTES.md` ส่วนที่ 1 อย่าเดา

## ขั้นที่ 3 — ตรวจก่อน merge

รายงานผลทีละข้อ:

1. `npm run verify` ผ่านหมดไหม
2. `git diff` — มีค่าลับ (key, token, password, connection string) หลุดเข้ามาไหม
3. ไฟล์ที่แก้อยู่ในขอบเขตบทบาทหรือเปล่า
4. เกณฑ์ "งานเสร็จ" ใน `AGENTS.md` §6 ครบทุกข้อไหม
5. ถ้าแตะ API หรือ schema → อัปเดต `docs/DESIGN.md` แล้วหรือยัง

**ถ้ามีข้อไหนไม่ผ่าน ให้บอกวิธีแก้ อย่าเพิ่งให้ merge**

## ขั้นที่ 4 — บันทึกสิ่งที่ตัวเองทำพลาด

ถ้ารอบนี้คุณ (agent) ทำอะไรผิดแล้วผู้ใช้ทักหรือแก้เอง
**ให้เพิ่มแถวใน `docs/NOTES.md` ส่วนที่ 3 ตามตรง** — สั่งอะไรไป / ผิดยังไง / ผู้ใช้จับได้ยังไง / แก้ยังไง

ข้อนี้เป็นส่วนหนึ่งของการให้คะแนนทีม ห้ามข้าม และห้ามเขียนให้ตัวเองดูดีกว่าความจริง

## ขั้นที่ 5 — บอกขั้นตอน merge

เสนอข้อความ commit ตาม Conventional Commits แล้วบอกคำสั่งที่ผู้ใช้ต้องพิมพ์
**อย่ารันเองทั้งหมด — ให้ผู้ใช้เป็นคนสั่ง merge และแก้ conflict เอง**

```bash
git add -A
git commit -m "<ข้อความที่เสนอ>"

git checkout dev
git pull                       # ดึงงานเพื่อนมาก่อน
git merge feature/<role>/<slug>   # ← ถ้า conflict ให้ผู้ใช้แก้เอง
git push
```
